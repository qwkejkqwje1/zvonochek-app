# ADR-0003. Чаты, почтовый ящик, файлы и перенос профиля (M4)

Статус: принято · 2 ноября 2026

## Контекст
M4 (ARCHITECTURE §6.7, §6.8, §17): переписка с контактами онлайн и офлайн (сообщение доходит, даже если отправитель
уже вышел), статусы, история, файлы с докачкой, перенос профиля на другой компьютер. Ограничения: только бесплатная
инфраструктура, сервер не должен видеть содержимое, Android следом (то же ядро).

## Решение
- **Кадры ZV4** (JSON, те же пути, что у звонка контакту): `chat {id, lc, ts, k, b, re?, f?}`, `chat_edit {id, m, b, ts}`,
  `chat_del {id, m}`, `chat_read {id, m}`, `chat_ack {ids}`, `chat_typing`, `chat_file_cancel {fid}`. id — ULID,
  порядок — время отправителя + счётчик Лэмпорта, дубли отсекаются по id.
- **Доставка:** всё, кроме `ack/typing/cancel`, лежит в очереди `outbox` до `chat_ack`. Живой путь — P2P-линк (iroh)
  или комната-ящик контакта (сигнализация: MQTT/Worker/Nostr/ntfy); через 8 с без подтверждения (или сразу, если
  контакт заведомо не в сети) — **почтовый ящик**; линк появился — повтор по линку. Раз в 30 с (и сразу при запуске
  P2P) ядро само поднимает линк к тем, кому есть что доставить.
- **Почтовый ящик устройства** (`zv-signal::mailbox`): адрес из секрета ящика (знают только контакты) → HKDF → id
  комнаты ChatRoom в Worker веба, токен и ключ AES-256-GCM внешнего слоя; внутри — конверт, запечатанный ключом пары.
  Предмет фиксированного размера 4124 байта (как blob ChatRoom веба — сервер не видит длину), длинные сообщения —
  частями. Кладём сразу в Worker ChatRoom (7–30 дней), Nostr (хранимые события kind 1 на 3 реле) и ntfy (кэш 12 ч);
  забираем через 4 с после запуска, раз в 10 мин и по кнопке в диагностике; курсор — в SQLite.
- **Файлы — свой протокол поверх потоков iroh вместо iroh-blobs:** предложение едет в сообщении
  (`f: {fid, name, size, mime, hash}`), байты — отдельным потоком линка: `{t: "get", fid, off}` → `{ok, size}` + байты
  с `off`. BLAKE3 всего файла, докачка из `.part` с места обрыва (в т. ч. после перезапуска), `Zone.Identifier`
  (MOTW) на Windows, до 4 ГБ, картинки до 25 МБ скачиваются сами, остальное — по кнопке, опасные расширения — с
  подтверждением. iroh-blobs добавил бы свой ALPN, хранилище и ~1 МБ кода ради возможностей (раздача многим,
  дедупликация), которые чату 1:1 не нужны.
- **История — SQLite** (`chats.db`, WAL, rusqlite bundled): `msgs`, `outbox`, `files`, `kv`. Как у десктоп-мессенджеров,
  лежит открыто в профиле пользователя (§13); секреты (ссылки, ключи пар, личность) — под DPAPI.
- **Веб:** ссылки на чат веба (`#chat=`) открываются в браузере; чат внутри звонка — как в вебе (DataChannel/`sig_chat`).
- **Перенос профиля:** файл `.zvp` = `MAGIC ‖ u32 длина заголовка ‖ заголовок JSON ‖ XChaCha20-Poly1305`; ключ —
  Argon2id (64 МиБ, 3 прохода, 4 линии; RFC 9106), заголовок — связанные данные AEAD, параметры KDF из файла
  ограничены (защита от «вечного» расчёта). Внутри — личность (ID устройства), контакты, ссылки, настройки, журнал
  звонков и снимок `chats.db` (`VACUUM INTO`), без самих файлов. Импорт проверяет всё, кладёт пакет в `import.pending`
  (под DPAPI) и перезапускает приложение; ядро применяет пакет при старте до чтения данных (недокачанные файлы
  начнутся заново в свою папку загрузок; отметки этого ПК — автозапуск, подсказка трея — свои).

## Последствия
+ Офлайн-доставка без своего сервера: три независимых хранилища, сервер видит только шифротекст одного размера и время.
+ Файлы идут напрямую (P2P) с проверкой и докачкой; меньше зависимостей и кода, чем с iroh-blobs.
+ Перенос на новый ПК без облака: контакты продолжают переписку с новым компьютером (тот же ID).
− Файлы — только когда оба в сети (ящик несёт лишь предложение); релей n0 ограничивает скорость, если прямой путь не
  пробился.
− Хранимые предметы в Nostr/ntfy живут по правилам чужих серверов (часы–дни); Worker — до 30 дней.
− Один профиль на двух ПК одновременно ломает доставку (один ID) — предупреждаем при сохранении.
