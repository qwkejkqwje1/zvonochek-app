# ADR-0008. Туннель звонка через P2P-линк приложений («как Hamachi»)

Статус: принято · 4 ноября 2026 · дополняет ADR-0001, ADR-0002, ADR-0007

## Контекст
Звонок идёт во встроенном веб-клиенте (ADR-0001): WebRTC браузера сам ищет путь — локальная сеть, пробитие NAT
(STUN), иначе TURN. У двух приложений при этом уже есть своя P2P-связь (iroh + libp2p, ADR-0002/0007), которая
пробивается там, где WebRTC не может: UPnP/NAT-PMP, свои релеи iroh по HTTPS, libp2p DCUtR. Бесплатных TURN
мало, они с квотами и бывают недоступны. Нужно, чтобы звонок приложение ↔ приложение мог пойти по этой связи, не
ломая прямой WebRTC и не трогая веб-клиент (он общий с сайтом).

## Решение
- **Кандидат ICE от ядра.** Для 1:1 звонка, когда комната привязана к P2P-линку (bind) и собеседник умеет туннель
  (`"tun": 1` в bind), ядро открывает UDP-сокет на IPv4 своего ПК (адрес маршрута по умолчанию; нет сети —
  127.0.0.1) и добавляет его в SDP собеседника, который получает окно звонка: строка
  `candidate:zvtun 1 udp 1526726655 <ip> <port> typ srflx raddr 0.0.0.0 rport 0` в первую m-секцию (max-bundle —
  транспорт один). Если описание собеседника пришло раньше, чем привязался линк, кандидат досылается отдельным
  `cand` (trickle, с `usernameFragment` этого описания).
- **Приоритет** 90<<24 — ниже host (126), prflx (110) и srflx (100), выше TURN (0–2): прямой WebRTC остаётся
  главным, туннель заменяет TURN. Тип `srflx` — чтобы веб показал «Напрямую (P2P)», а не «Локальная сеть».
- **Пересылка.** Пакет браузера на этот сокет → собеседнику датаграммой линка: `T` + 8 знаков комнаты + пакет
  (по лучшему пути iroh). Не влезло в датаграмму или пути iroh нет — кадр `{"t":"tun","r":комната,"d":base64}` по
  потоку линка (надёжно, по порядку). У собеседника ядро отдаёт пакет своему браузеру со своего такого же сокета.
  Каждый браузер видит другого по адресу своего ядра; проверки ICE (STUN), DTLS и SRTP проходят насквозь — ядро
  ничего не расшифровывает.
- **Куда отдавать.** Адрес браузера ядро узнаёт по первым пакетам на сокет (только с адреса самого ПК или
  127.0.0.1 — чужие пакеты из сети отбрасываются). Браузер стучится с нескольких своих сокетов: адрес меняется на
  новый, если с него пошли DTLS/медиа (выбранная пара) или прежний молчит дольше 3 с. Пакеты от собеседника идут
  только своему браузеру — открытого ретранслятора нет.
- **Ограничения.** Только 1:1 (в групповой сетке P2P к комнате не привязывается). Линк только через релей libp2p —
  пакеты не шлём: у публичных релеев лимит цепи (~2 мин / 128 КБ), медиа порвёт линк; браузер выберет TURN.
- **Настройка** «Звонки через P2P-туннель» (`tunnel`, по умолчанию включена; нужна у обоих). Диагностика — строка
  «туннель звонка» в «Прямых соединениях» (`p2p_status.tunnels`: пакеты в обе стороны, кадрами, не отправлено).
  Проверка: `ZV_TUNNEL_ONLY=1` — ядро убирает из SDP собеседника все кандидаты, кроме туннеля.

## Последствия
- Звонок двух приложений соединяется там, где WebRTC не пробивается, а P2P-связь есть (UPnP, релей iroh по
  HTTPS 443, DCUtR), без TURN и его квот. Задержка — как у пути линка; через релей iroh — как через TURN.
- Ничего не меняется для звонков с браузером и в группах; веб-клиент не тронут; со старыми приложениями (без
  `tun` в bind) туннель не включается.
- Лишнего трафика без надобности нет: пока браузеры говорят напрямую, через туннель уходят только редкие проверки.
- E2E `tests/e2e/devhost-tunnel.mjs`: только туннель поверх iroh (датаграммы) и libp2p (кадры) — голос и видео
  в обе стороны; обычный звонок (выбрана локальная сеть, туннель запасной); туннель выключен у одного — его нет.
