# ADR-0007. libp2p — второй P2P-транспорт рядом с iroh; один линк на несколько путей

Статус: принято · 4 ноября 2026 · дополняет ADR-0002

## Контекст
ADR-0002 отложил libp2p: его роль «второго пути» закрывали каналы сигнализации. Но остались зависимость от
инфраструктуры n0 (релеи iroh, поиск по ID через DNS n0) и разрыв линка при смене сети или пропаже пути. Нужно:
второй независимый транспорт со своими релеями, поиском и пробитием NAT; соединение не рвётся, пока жив хотя бы
один путь, и само переходит на лучший. Только бесплатная инфраструктура.

## Решение
- **libp2p 0.57** (`crates/zv-p2p/src/lp.rs`): QUIC v1 и TCP (Noise + Yamux), порт 47322 (занят — любой);
  identify, ping, Kademlia (клиент, бутстрап Amino/IPFS), relay-клиент + DCUtR, AutoNAT, UPnP, mDNS (не на Android),
  libp2p-stream. Протоколы `/zv/4/ctl` (кадры линка) и `/zv/4/f` (потоки файлов). Ключи RSA поддерживаются: они
  у бутстрап-узлов IPFS (без этого DHT недоступна); свои ключи — Ed25519.
- **Тот же ключ.** PeerId libp2p выводится из того же Ed25519-ключа устройства, что EndpointId iroh: ID контакта
  прежний, ID ↔ PeerId без обмена, Noise доказывает владение тем же ключом.
- **Поиск собеседника:** подсказка `l` (multiaddr с `/p2p/<ID>`: по два внешних, в локальной сети и через релей) — в
  hello `zv`, сообщениях контактов и составе групп; в код приглашения — один прямой и один через релей (код не
  разрастается). Без подсказки — провайдер-запись в DHT по ключу sha256(`zv4/presence/`‖PeerId) (публикуется при
  внешних адресах, раз в 30 мин) и mDNS в локальной сети.
- **Релеи:** AutoRelay-lite — до двух резерваций у публичных узлов с hop-протоколом (находятся через identify),
  через релей — DCUtR; после прямого соединения релейное закрывается. Публичные релеи ограничивают цепь
  (обычно 2 мин / 128 КБ) — это путь для сигнализации и пробития, не для медиа.
- **Мультипуть.** `LinkId` — логический линк из путей iroh и libp2p (в `hello4` флаг `"mp":1`; со старыми 4.0 —
  как раньше, линк на соединение). `connect()` дозванивается обоими транспортами параллельно: первый даёт линк,
  второй добавляется путём. Основной путь — по оценке «iroh прямой > libp2p прямой > iroh релей > libp2p релей»
  с удержанием текущего; кадры и потоки файлов — по основному, датаграммы (голос) — по лучшему пути iroh, без
  него голос идёт кадрами потока. Пропал путь —
  линк продолжает работу по другому; пропали все — 5 с ожидания с повторным дозвоном, затем `LinkDown`.
  Дубли одного транспорта схлопываются (остаётся путь, открытый стороной с меньшим ID).
- **Живость путей libp2p.** У потоков нет датаграмм, а «зомби»-соединение (NAT забыл привязку, TCP молчит) не
  видно сразу → `pk4` каждые 10 с тишины, путь мёртв после 35 с; при переходе на прямое — проба с ответом за 3 с.
- **Настройка** «Второй транспорт (libp2p)» (по умолчанию включён, переключение перезапускает P2P-узел);
  `ZV_P2P_ONLY=iroh|libp2p` — один транспорт для отладки. Диагностика: транспорт и пути линка, NAT, UPnP, релеи, DHT.

## Последствия
+ P2P работает без n0: локальная сеть (mDNS), прямые адреса и UPnP, публичные релеи libp2p, поиск по DHT.
+ Смена сети или пропажа одного транспорта не рвёт чат, передачу файла и P2P-канал звонка.
+ Попутно исправлено: чтение кадров и датаграмм в одном `select!` могло терять частично прочитанный кадр.
− Больше зависимостей и размер exe (по архивам CI: +3 МБ сжатого, exe ≈ +7 МБ); больше фоновых соединений
  (DHT, резервации релеев), на Android без mDNS.
− У libp2p нет датаграмм: если остался только его путь, голос моста идёт кадрами надёжного потока (задержка
  при потерях выше).

## Примечание о ключе
В ARCHITECTURE (D6) планировались отдельные ключи iroh и libp2p. Выбран один ключ: тогда ID контакта однозначно
задаёт оба адреса, а подмену транспорта исключает сама криптография (Noise libp2p проверяет тот же открытый ключ).
Домены подписей не пересекаются: TLS 1.3 iroh подписывает `CertificateVerify` со своим контекстом, Noise libp2p —
строку `noise-libp2p-static-key:` + ключ, подписи групп — свой формат.
