## 0. Коротко

- **Что делаем:** нативное приложение ZVONochek для Windows (потом Android): ядро на **Rust** + окно на **Tauri 2 / WebView2**.
- **Совместимость:** звонок по ссылке `https://zvonochek.github.io/#k=…` (раньше — `qwkejkqwje1.github.io/zvonochek`) работает между браузером и приложением
  **без изменений веба**. Голос и видео — WebRTC внутри WebView2 (тот же Chromium, что у веба: эхоподавление, кодеки, демонстрация экрана).
- **Между приложениями** — свой P2P-слой: **iroh** (основной: QUIC, пробитие NAT, релеи, постоянный ID) +
  **libp2p** (поиск собеседника без серверов через DHT, второй независимый маршрут, TCP).
- **Надёжность** = все маршруты параллельно, лучший — основной, второй — горячий резерв. Не «больше способов обхода NAT»
  (их по сути три: напрямую/LAN, пробитие UDP, релей), а быстрое переключение между ними.
- **Бесплатно и без карт:** публичные MQTT/Nostr/ntfy, Worker веба, релеи n0 и IPFS, GitHub Actions и Releases.
- **Порядок:** M0 фундамент → M1 совместимый сигналинг и звонок на тестовом стенде → **M2 Windows 4.0-beta** →
  M3 P2P и контакты (4.0) → M4 чаты и файлы → M5 группы → M6 Android.

## 1. Ключевые решения

| # | Решение | Почему |
|---|---|---|
| D1 | Rust + Tauri 2 (WebView2); сначала Windows 10/11 x64, ARM64 — попутно | iroh и rust-libp2p нативные; установщик ~10 МБ; тот же код пойдёт на Android |
| D2 | Медиа — WebRTC внутри WebView, своего медиастека нет; экран звонка — встроенный веб-клиент с заменённым `signaling.js` (ADR-0001) | полная совместимость с вебом (это его код); эхоподавление/шумодав/АРУ Chromium; видео и экран |
| D3 | Сеть, крипто и данные — только в ядре; UI тонкий; **никакого HTTP-сервера на localhost** (в 3.0 был) | работает при закрытом окне; Worker веба пускает запросы без Origin, а из WebView с чужим Origin — нет; меньше поверхность атаки |
| D4 | Протокол веба = спецификация + тест-векторы из `crypto.js` + E2E с закреплённым коммитом + ночной тест против живого сайта | веб будет меняться (идёт новая версия) — о поломке узнаём в тот же день |

| D7 | Контакт = постоянная комната (парный секрет) + ключи устройств | если P2P не находится, звонок идёт через те же каналы, что у веба |

| D9 | Горячий резерв голоса через QUIC-датаграммы iroh (приложение↔приложение); с браузером — мост веба `voice2` | обрыв основного пути почти не слышен |

| D13 | Тестовый стенд `zv-devhost`: ядро без окна + IPC по WebSocket → UI в обычном Chromium (Playwright) | автотесты звонков веб↔приложение в CI на Linux (у WebKitGTK нет нормального WebRTC) |

## 2. Цели и рамки

**Цели по приоритету**
1. Звонки: стабильнее, чем браузер↔браузер; входящий при закрытом окне; автозапуск с Windows.
2. Чаты между приложениями (с офлайн-доставкой) и файлы.
3. Платформы: Windows 10/11 → Android. iPhone — веб/PWA (нативный iOS требует $99 в год).
4. До ~50 пользователей, открытый код на GitHub, ноль затрат.

**Совместимость с вебом (обязательно):** звонки по ссылке 1:1 и групповые (до 6 человек, как в вебе), чат и файлы внутри звонка,
одинаковый код безопасности, режимы «только TURN» и мост.

**Не делаем:** сетевую совместимость со Звоночком 2.x/3.0 (пользователей нет), свои платные серверы, SFU, аккаунты, нативный iOS.
На старте не поддерживаем привязку устройств `#link=` и «Мой номер» веба — позже, если понадобится (см. 5.9);
веб-чаты `#chat=` — с 4.2 в окне «Чаты сайта» (встроенный веб-клиент, ADR-0009).

**Что конкретно значит «стабильнее»**
- Сигналинг живёт в ядре, а не во вкладке (браузер усыпляет фоновые вкладки и рвёт их WebSocket).
- Больше путей к тем же брокерам: например, MQTT по TCP 1883 к тем же 5 брокерам — брокер общий, сообщения доходят до веба,
  а ТСПУ «замораживает» прежде всего TLS-соединения к зарубежным адресам.
- Между приложениями — прямой P2P (iroh/libp2p), горячий резерв голоса, локальная сеть без интернета, VirtualBox.
- Автопереподключение после сна и смены сети; данные не пропадают при очистке браузера.

Честно: звонок **браузер↔приложение** по медиа не лучше браузер↔браузер (с обеих сторон WebRTC) — выигрыш в сигналинге и работе в фоне.
Большой выигрыш — **приложение↔приложение**.

## 3. Общая схема

```text
┌───────────────────────────── ZVONochek.exe (Tauri 2) ─────────────────────────────┐
│ WebView2: главное окно · окно входящего звонка                                      │
│ ┌────────────────────────────────────────────────────────────────────────────────┐ │
│ │ UI (JS без сборки): ссылки · контакты · чаты · история · настройки · диагностика│ │
│ │ окно звонка = встроенный веб-клиент v39 как есть (WebRTC, группы, чат, файлы,   │ │
│ │   мост); заменён только signaling.js → мост к ядру; + desktop/preload.js        │ │
│ └──────────────▲──────────────────────────────────────────────┬──────────────────┘ │
│     события и бинарные каналы (Tauri IPC)               команды (invoke)            │
│ ┌──────────────┴──────────────────────────────────────────────▼──────────────────┐ │
│ │ zv-core: комнаты · звонки · контакты · чаты · файлы · присутствие · хранилище   │ │
│ │  ├─ zv-signal: RoomHub ⇄ каналы веба: Worker WS/HTTP · MQTT WSS/TCP · Nostr · ntfy│ │
│ │  │             + канал p2p (поток iroh / libp2p)                                │ │
│ │  ├─ zv-net:   личность · iroh Endpoint · libp2p Swarm · PathManager · LAN/ВМ     │ │
│ │  └─ zv-proto: ссылки · deriveRoom · seal/open · сообщения · код безопасности     │ │
│ └────────────────────────────────────────────────────────────────────────────────┘ │
│ трей · автозапуск · один экземпляр · zvonochek:// · уведомления · обновления        │
└─────────────────────────────────────────────────────────────────────────────────────┘
     │ WebRTC (DTLS-SRTP; ICE: STUN/TURN)              │ QUIC (iroh) · TCP/QUIC (libp2p)
     ▼                                                 ▼
 браузер с веб-версией или другое приложение      другое приложение: напрямую или через релей
```

- Один процесс: ядро на tokio + окна WebView2 (их процессы `msedgewebview2.exe` отдельно).
- Окно закрыто → ядро остаётся в трее (~30–40 МБ ОЗУ), WebView выгружается. Входящий звонок → создаётся маленькое окно.
- UI ↔ ядро: команды (`invoke`) и события; бинарные кадры голоса — через каналы Tauri (`ipc::Channel`).

## 4. iroh + libp2p: кто за что отвечает

> **M3 (ADR-0002):** реализован только iroh; libp2p отложен — второй путь дают каналы сигнализации (ящики контактов).
> **4.1 (ADR-0007):** libp2p — второй транспорт; линк собирается из путей обоих транспортов и переходит на лучший без
> разрыва. Ключ libp2p — тот же Ed25519-ключ устройства (а не отдельный, как в D6). Таблица ниже — исходный план.
> **4.2 (ADR-0008):** туннель звонка — 1:1 звонок приложений может идти по линку: ядро даёт веб-клиенту кандидат ICE
> (UDP-сокет на своём ПК, приоритет ниже прямых, выше TURN) и пересылает пакеты датаграммами `T` или кадрами `tun`.

| Задача | iroh | libp2p |
|---|---|---|
| Постоянный ID устройства | ✅ EndpointId (Ed25519) | PeerId (ключ из того же мастер-ключа) |
| Основной транспорт приложение↔приложение | ✅ QUIC: потоки + датаграммы | резерв: TCP/QUIC, Noise, Yamux |
| Пробитие NAT | ✅ встроенное (координация через релей) | ✅ DCUtR — второй, независимый механизм |
| Если напрямую нельзя | ✅ релеи n0 (HTTPS, TCP 443) или свой iroh-relay | relay v2: публичные релеи IPFS ограничены (только для DCUtR), свой `zvonochek-relay` из 3.0 — полноценный |
| Найти адрес по ID | ✅ DNS/pkarr (n0) + pkarr в Mainline DHT | Kademlia (IPFS Amino DHT) |
| Найти собеседника по комнате без серверов | — | ✅ provider-записи Kademlia по хешу топика |
| Локальная сеть | ✅ mDNS | ✅ mDNS (дубль дешёвый) + маяк VirtualBox из 3.0 |
| Сеть без UDP | ✅ через релей (TCP 443) | ✅ прямой TCP |
| Файлы | ✅ iroh-blobs (BLAKE3, докачка) | — |
| Голос резерва | ✅ QUIC-датаграммы | поток (если доступен только libp2p) |

**Почему оба.** iroh лучше всего соединяет «из коробки»: мгновенный старт через релей и прозрачный переход на прямой путь.
Но поиск по ID и релеи — инфраструктура n0 (бесплатно, с лимитами, без гарантий). libp2p добавляет независимость:
рандеву без серверов (DHT), TCP-маршрут, свои релеи. libp2p — за feature-флагом `libp2p`; на Android по умолчанию выключим, если замеры батареи будут плохими.

**Личность.** Мастер-сид 32 байта (DPAPI) → HKDF → ключ iroh, ключ libp2p, ключ шифрования секретов в БД.
ID устройства = EndpointId. PeerId сообщается внутри уже аутентифицированного соединения и привязывается к EndpointId в записи контакта.

**Рандеву через DHT.** Ключ = multihash SHA-256 от `"zv4/rdv" ‖ topic ‖ номер 10-минутного окна`. Оба участника делают
PROVIDE и ищут провайдеров (текущее и прошлое окно) → получают PeerId и адреса без MQTT/Worker/Nostr. Это медленно (5–30 с),
поэтому только запасной путь. Посчитать ключ может лишь тот, кто знает секрет комнаты.

**Гонка подключений к известному собеседнику**
```text
t = 0      iroh connect(EndpointAddr: релей + адреса из hello/контакта; поиск: DNS/pkarr → Mainline DHT → mDNS)
t = 0      известен LAN-адрес или маяк ВМ → прямая попытка iroh
t = 1,5 с  нет iroh-соединения → libp2p: известные адреса → FIND_PEER в DHT → relay v2 + DCUtR
первое удачное соединение — основное; второе (если поднялось) держим горячим резервом на время звонка
```
PathManager раз в 2 с оценивает RTT и потери (статистика путей iroh, ping libp2p, статистика WebRTC) и при необходимости переключает.

**Лестница маршрутов звонка между приложениями** (одновременно живут основной и один резервный):
1. WebRTC напрямую (ICE host/srflx) — основной медиаканал: видео, эхоподавление, контроль перегрузки.
2. WebRTC через TURN — как в вебе (Worker `/turn` → Metered → статический TURN).
3. Горячий резерв голоса: Opus-кадры по iroh (QUIC-датаграммы) — напрямую или через релей n0.
4. libp2p: прямой TCP / relay v2 + DCUtR / свой relay.
5. Мост через каналы сигналинга (`voice2` через Worker/MQTT/Nostr), как в вебе, — последний рубеж.

Видео на ступенях 3–5 — H.264 через WebCodecs с низким битрейтом (как мост веба) или отключено.

## 5. Совместимость с веб-версией («протокол ZVONochek v1»)

Эталон — код веба на закреплённом коммите `a61b11e` (v39). Из него делаем `spec/WEB-PROTOCOL-v1.md` и `spec/vectors/*.json`.

### 5.1 Ссылки
- Звонок: `https://zvonochek.github.io/#k=<секрет base64url, ≥ 22 символа>[&d=<32 hex>]`;
  `&d=` (персональный номер веба) пока только распознаём.
- `#chat=` (с 4.2) — окно «Чаты сайта» (ADR-0009); `#link=` не поддерживаем — показываем «не поддерживается».
- Своя схема: `zvonochek://call#k=…` (то же содержимое; секрет остаётся во фрагменте и в логи не пишется).

### 5.2 Криптография (zv-proto, проверяется векторами)
- `deriveRoom`: HKDF-SHA256(секрет, salt `ZVONochek/v1`): info `topic` → 128 бит, hex — топик; info `aes-256-gcm` → ключ.
- `seal`: JSON → если > 300 байт и нет `_noZip`, deflate-raw (тег `z2`, иначе `z1`) → AES-256-GCM, IV 12 байт,
  AAD = топик + тег → строка `тег.b64u(iv).b64u(шифротекст)`.
- Код безопасности: SHA-256 отсортированных строк `a=fingerprint` (в верхнем регистре) обоих SDP → 5 эмодзи из 64 + 6 цифр;
  у моста — от `bridge#topic#ids`.
- Векторы генерирует Node 24, исполняя `crypto.js` веба (с небольшими заглушками). В CI проверяем в обе стороны:
  Rust `seal` → JS `open` и JS `seal` → Rust `open`.

### 5.3 Конверт и дедупликация
`{...сообщение, from: 16 hex (на сессию), inst: 12 hex (на загрузку), mid: "u32-u32", ts}`. Одно сообщение приходит по нескольким
каналам — дубли отбрасываем по `mid`.

### 5.4 Каналы (все параллельно, как в `signaling.js`)

| Канал | Адрес | Особенности |
|---|---|---|
| MQTT ×5 (WSS) | `public.cloud.shiftr.io` (public/public), `broker.emqx.io:8084`, `broker.hivemq.com:8884`, `test.mosquitto.org:8081`, `mqtt.eclipseprojects.io` | топик `zvonochek/v1/<topic>`, QoS 0 |
| MQTT ×5 (TCP 1883) — **только приложение** | те же брокеры | дублёр без TLS: полезная нагрузка всё равно зашифрована AES-GCM; веб получает сообщения через тот же брокер |
| Worker веба | `wss://zvonochek.zerewgwe.workers.dev/room/<topic>?peer=…` | важные пакеты дублируются HTTP POST; запасной HTTP-опрос `?peer=&since=` |
| Nostr ×9 | damus, nos.lol, primal, nostr.mom, offchain.pub, snort, nostr.band, wellorder, nostr.info | kind 29333 (эфемерные), тег `t` = `zv-<topic>`, одноразовый ключ |
| ntfy.sh | топик `zv1-` + первые 48 hex SHA-256(топика) | только hello/hi/ack/reset/bye/desc/cand/full (+ групповые); hello не чаще раза в 30 с; голос — никогда |

- Все WSS-соединения (MQTT, Worker, Nostr) ротируются после ~9000 принятых байт по схеме «сначала новое, потом закрыть старое» —
  защита веба от «заморозки» ТСПУ после ~16 КБ. Повторяем один в один.
- Голос моста — только первые 2 MQTT, Worker и 2 Nostr (как в вебе).
- Worker пускает запросы без заголовка Origin (а из WebView с Origin `tauri.localhost` — нет), поэтому вся сеть, включая TURN-запрос, — в ядре.

### 5.5 Сообщения
`hello{name, ver, bc, vc}`, `hi`, `ack{ackType}`, `reset`, `desc{desc, gen, to, toInst}`, `cand{cand, gen, to, toInst}`,
`voice` (мост v1), `voice2` (мост v2, WebCodecs Opus, `_noZip`), `sig_chat`, `g_hi/g_desc/g_cand/g_chat` (группы), `bye`, `full`.

### 5.6 Логика звонка (не переписываем — это код веба; для справки)
- polite = `selfId < from собеседника`; perfect negotiation с обработкой коллизий.
- `RTCPeerConnection`: `bundlePolicy: max-bundle`, `iceCandidatePoolSize: 1`, `iceTransportPolicy: relay` в режиме «только TURN»; те же 10 STUN.
- DataChannel (negotiated): `ctrl` id 0 — JSON `state{mic,cam,name}`, `vcap{h,fps}`, `chat{text}`; `file` id 1 — JSON `start`… + бинарные куски (до 256 МБ).
- Тайминги: SDP через 450 мс сбора, полный SDP — через 1,8 с, повтор до `ack`; TURN лениво через 6 с + `restartIce`;
  мост автоматически через 10 с без соединения; сторож 13,5 с (impolite) / 19 с (polite) +7 с продления → новая попытка `gen+1` и `reset`;
  собеседник «устаревает» через 30 с, запись ростера — через 90 с.

### 5.7 Версия (`ver`)
Веб пишет «обновите страницу», если `ver` собеседника отличается от его версии. Поэтому:
- приложение отправляет `ver` = версия веба, с которой оно проверено;
- ночной тест против живого сайта при успехе публикует `compat.json` (проверенные версии веба). Приложение раз в сутки читает его
  и `version.json` сайта: живая версия проверена → отправляем её; нет → отправляем свою и предлагаем обновить приложение;
- свои поля: `app: "zvd"`, `av: "4.0.0"`, `zv: {…}` (раздел 6.3) — ядро добавляет их в исходящие `hello`/`hi`. JS веба читает только известные поля.
- v2: так как окно звонка — встроенный веб-клиент, `ver` = версия встроенной копии автоматически. Новая версия веба →
  ночной тест это видит → синхронизируем копию (`tools/sync-web.sh`) и выпускаем обновление.

### 5.8 Предложения для новой веб-версии (необязательно, по 5–20 строк)
1. `hello` с `app: "zvd"` → не показывать предупреждение о версии, писать «собеседник в приложении ZVONochek».
2. Кнопка «Открыть в приложении» → `zvonochek://call#k=…`.
3. Правило: несовместимые изменения крипто/формата — только с новой солью (`ZVONochek/v2`) или новым типом сообщения, чтобы старые клиенты не ломались молча.
4. Сообщение `ringing` от приложения → веб показывает «Звоним… собеседник в приложении ZVONochek» вместо подсказки «Собеседник пока не найден» через 25 с.

### 5.9 Защита от изменений веба и что позже
- Закреплённый коммит в E2E; ночной прогон против живого сайта (провал → автоматический issue); быстрый выпуск через автообновление.
- Позже по необходимости: привязка устройств, «Мой номер» (inbox с подписями ECDSA P-256). Веб-чаты `#chat=` — с 4.2
  без переписывания chat.js: окно встроенного веб-клиента, WebSocket к Worker через ядро (ADR-0009).

## 6. Сценарии

### 6.1 Звонок по ссылке: приложение ↔ браузер
1. Вставить ссылку (или открыть `zvonochek://…`), либо «Создать ссылку» и отправить её.
2. Ядро: ссылка → deriveRoom → RoomHub поднимает каналы (5.4).
3. Движок шлёт `hello` (как веб) с `ver` по 5.7; браузер отвечает `hi`; роли — по правилу polite.
4. `desc`/`cand` с `gen`, `to`, `toInst` и `ack` → ICE → DataChannel → звонок; код безопасности одинаковый у обоих.
5. Нет соединения: 6 с — TURN (ядро получает серверы у Worker `/turn` → Metered → статический) и `restartIce`; 10 с — мост `voice2`;
   сторож — `reset` и новая попытка.
6. Завершение — `bye`; запись в истории; кнопка «Сохранить ссылку» (контакт-ссылка с именем).

### 6.2 «Мои ссылки»: звонок из браузера в трей
- Постоянные ссылки с именами («Для всех», «Мама», «Работа»); секреты — в профиле. Ссылка фактически = контакт для человека без приложения.
- Ядро в трее слушает все свои ссылки экономно: MQTT (2 брокера, TCP + WSS), Worker WS (без HTTP-опроса в простое — у бесплатного Worker
  лимит запросов в сутки), 2 Nostr, ntfy.
- Человек открывает ссылку в браузере → его `hello` приходит → окно «Звонит Анна — ссылка „Мама“» + мелодия + уведомление.
  «Ответить» → окно звонка → `hello`/`hi` → дальше как 6.1. «Отклонить» → `bye`. До ответа приложение молчит.
- «Сменить ссылку» (старая перестаёт работать), «Не беспокоить».
- Работает с текущим вебом без изменений: для браузера это обычная комната, где собеседник ответил чуть позже.
- Браузер повторяет `hello` каждые 4,5 с и ждёт без ограничения, поэтому звонок дойдёт, даже если приложение запустилось уже после того,
  как человек открыл ссылку. Через 25 с веб показывает подсказку «Собеседник пока не найден…» — работе не мешает (улучшение — 5.8, п. 4).
- Человек закрыл страницу, не дождавшись ответа, → «пропущенный по ссылке „Мама“».

### 6.3 Приложение ↔ приложение по ссылке: апгрейд на P2P
- В `hello` приложение добавляет `zv: {id: EndpointId, pid: PeerId, relay, addrs, caps}`.
- Увидев `zv` собеседника, ядра соединяются (гонка, раздел 4) и обмениваются `bind` — доказательством знания секрета комнаты.
- В RoomHub появляется канал `p2p` (самый быстрый); WebRTC-сигналинг дублируется через него; после соединения публичные каналы
  переходят на редкий пульс (экономим бюджеты).
- Запускается горячий резерв голоса (6.6).
- После звонка — «Сохранить в контакты»: запрос по `p2p`, собеседник подтверждает, обе стороны сохраняют контакт (6.4).

### 6.4 Контакты
- Способы: после звонка (основной); код приглашения `zv4:…` (ID, адреса, одноразовый секрет; 7 дней, «Новый код» отзывает старый — как в 3.0);
  «Рядом» — mDNS в LAN и маяк VirtualBox (`10.0.2.2:47329`, `192.168.56.1`); позже QR на Android.
- Запись: человек → устройства [EndpointId, PeerId, последние адреса и релей, когда видели] + парный секрет 32 байта
  (генерирует сторона с меньшим EndpointId, передаёт по защищённому P2P-каналу).
- Из парного секрета — «комната контакта» (тот же deriveRoom): запасной путь через MQTT/Worker/Nostr/ntfy, если P2P не нашёлся.
- Код безопасности контакта: 5 эмодзи + 6 цифр от SHA-256(отсортированные EndpointId). Сверить голосом один раз → «проверен».
- Структура «человек → несколько устройств» закладывается сразу (под Android и второй ПК).

### 6.5 Звонок контакту при закрытом окне
1. Вызывающий создаёт `call_id` и шлёт `ring{call_id, video, name}` параллельно: iroh (по EndpointId), libp2p (через 1,5 с),
   комната контакта (через 3 с, если P2P нет).
2. У принимающего (трей): окно входящего + мелодия + уведомление. Дубли `ring` по разным каналам схлопываются по `call_id`.
3. «Ответить» → окно звонка → сигналинг по самому быстрому каналу + резерв голоса. «Отклонить» → `ring_decline`. Уже в звонке → `busy`.
4. Нет ответа 45 с → `ring_cancel`, «пропущенный» у обоих. Собеседник не в сети → «не в сети», предложить сообщение (M4).

### 6.6 Горячий резерв голоса (приложение ↔ приложение)
- Параллельно с WebRTC шлём Opus-кадры (WebCodecs, 20 мс, ~24 кбит/с, DTX) по лучшему P2P-пути — QUIC-датаграммами iroh
  (если есть только libp2p — потоком).
- Получатель играет WebRTC. Пропал звук WebRTC > 300 мс (по `inbound-rtp` не растёт `packetsReceived`), а резервные кадры идут →
  играем резерв (AudioWorklet, джиттер-буфер 60–120 мс); WebRTC тем временем делает ICE restart. Обратно — после 3 с стабильной работы, плавно.
- Цель: разрыв звука < 0,5 с при обрыве основного пути. Эхоподавление для резерва (воспроизведение через тот же WebView, как мост веба) — проверяем прототипом в начале M3.
- С браузером аналог — мост веба `voice`/`voice2`; приложение поддерживает его полностью.

### 6.7 Чаты (M4, ADR-0003)
- Онлайн — по P2P-линку или через комнату-ящик контакта; статусы «отправлено → в ящике → доставлено → прочитано»
  (отчёты о прочтении можно выключить), «печатает…», ответ, правка, удаление у себя и у всех.
- Офлайн — «почтовый ящик устройства»: адрес из секрета ящика (его знают только контакты) → комната ChatRoom в Worker
  веба + хранимые события Nostr (3 реле) + кэш ntfy 12 ч; предмет фиксированного размера (4124 байта), внутри —
  конверт, запечатанный ключом пары. Через 8 с без подтверждения — в ящик; получатель забирает при запуске и раз в 10 мин.
- id сообщения — ULID; порядок — время отправителя + счётчик Лэмпорта; дедуп по id; история — SQLite.
- В звонке с браузером — чат веба (`ctrl` → `chat`, без DataChannel — `sig_chat`); ссылки на чат веба `#chat=` —
  окно «Чаты сайта» (с 4.2, ADR-0009).

### 6.8 Файлы
- Между приложениями: свой протокол поверх потоков iroh (вместо iroh-blobs, ADR-0003): предложение в сообщении,
  байты — по запросу `{t: get, fid, off}`; BLAKE3, докачка из `.part` с места обрыва (и после перезапуска), до 4 ГБ.
  Картинки до 25 МБ — сами, остальное — по кнопке; метка «из интернета» (MOTW); опасные расширения — с подтверждением.
- В звонке с браузером — протокол веба по DataChannel `file` (до 256 МБ).

### 6.9 Группы и групповые звонки (M5, ADR-0004)
- Совместимо с `group.js`: mesh до 6 человек (`MAX_REMOTE_PEERS = 5`), `g_hi/g_desc/g_cand/g_chat` в той же комнате; смешанные группы браузеры + приложения.
- Группы контактов (до 6 устройств): общий секрет → комната и почтовый ящик группы; сообщения подписаны ключом
  устройства автора; переписка и файлы — как в чатах 1:1, участники могут не быть контактами друг друга.
- Звонок группе = `g_ring` всем участникам + «Присоединиться» в ленте; сигнализация — обычными транспортами комнаты
  (в mesh нет попарных P2P-линков), медиа — напрямую по WebRTC.

## 7. Протокол между приложениями (ZV4)

| Что | Как |
|---|---|
| Транспорт | iroh ALPN `zv/4` (основной), libp2p-протокол `/zv/4` (резерв) |
| Управляющий поток | двунаправленный поток; кадр = длина u32 BE + JSON UTF-8, ≤ 256 КБ |
| Голос резерва | QUIC-датаграмма: `ver(1) call(2) seq(2) ts(4) flags(1)` + Opus, ≤ 1200 байт; в libp2p — отдельный поток с теми же кадрами |
| Файлы | отдельный поток того же линка: `{t: "get", fid, off}` → `{ok, size}` + байты с `off` (BLAKE3, докачка) |
| Первое сообщение | `hello4{proto: 1, app: "4.0.0", caps: […], name}`; неизвестные поля и типы игнорируются |
| Допуск | удалённый ID — контакт; или в первые 5 с валидный `bind`; или секрет кода приглашения. Иначе — закрыть. Лимиты частоты |
| Типы | `hello4`, `bind`, `ping/pong`, `presence`, `contact_offer/accept/decline`, `ring/ring_accept/ring_decline/ring_cancel/busy`, `sig{call_id, m}` (обёртка над сообщениями веб-протокола), `chat`, `chat_edit`, `chat_del`, `chat_read`, `chat_ack`, `chat_typing`, `chat_file_cancel` (файл — поле `f` в `chat`), `bye` |
| Версии | `proto` + `caps`; минимальная поддерживаемая версия; несовместимость → понятное «обновите приложение» |

`bind = {topic, proof}`, где `proof = HMAC-SHA256(K_bind, "zv4-bind" ‖ мой EndpointId ‖ его EndpointId)`,
`K_bind = HKDF(секрет комнаты, salt "ZVONochek/v1", info "zv4-bind")`. Доказывает знание секрета и привязан к паре ID — переиграть нельзя.

## 9. Ядро изнутри

- **Модель:** tokio; каждый сервис — актор (задача + очередь). Наружу — фасад `Core` с async-методами и поток событий `Event`.
- **RoomHub:** `join(link)` → ключи → каналы по политике → `send(msg, class)`: конверт (`from`, `inst`, `mid`, `ts`) → seal → рассылка;
  приём: open → дедуп по `mid` (LRU 4096 / 10 мин) → подписчикам (UI, CallRegistry).
- **Трейт `Channel`:** `send(sealed, class)`, `inbound()`, `status()`. Реализации: `MqttWss`, `MqttTcp`, `WorkerWs`, `WorkerHttp`, `Nostr`, `Ntfy`, `P2p`.
- **Политика классов** (точно — по spec, снятой с `signaling.js`):

| Класс | Сообщения | Каналы |
|---|---|---|
| hello | hello, hi, g_hi | все; ntfy — не чаще раза в 30 с |
| critical | desc, cand, ack, reset, bye, full, g_desc, g_cand | все + HTTP-дубль в Worker |
| voice | voice, voice2 | 2 MQTT + Worker + 2 Nostr; не ntfy |
| chat | sig_chat, g_chat | как в вебе |
| zv4 | сообщения ZV4 | только p2p |

- **Живучесть:** ротация WSS после 9000 байт; переподключение с экспоненциальной задержкой; смена сети / выход из сна (события Windows) →
  немедленное переподключение всех каналов и `network_change()` у iroh.
- **CallRegistry** (один активный звонок): `idle → ringing_out | ringing_in → connecting → active → ended(reason)`;
  причины: hangup, declined, busy, missed, cancelled, failed. Второй входящий во время звонка → `busy` + «пропущенный».
- **PathManager:** для каждого собеседника — пути (WebRTC напрямую/TURN, iroh напрямую/релей, libp2p, мост) с RTT и потерями;
  выбирает основной, держит один резерв, публикует событие для индикатора маршрута.
- **Store:** SQLite (WAL) в отдельном потоке, миграции, транзакции.

## 11. Интерфейс

- **Окна:** главное (закрытие → трей), «Входящий звонок» (маленькое, поверх всех, создаётся по требованию), звонок — в главном окне.

- **Оболочка** — из 3.0 (`app.js`, `settings.js`, `theme.js`, `audio.js`, `worklet.js`), светлая/тёмная тема.
- Язык — русский (как у веба).

## 13. Данные

- Каталог: Windows — `ZVONochek-data` рядом с exe (раньше `%APPDATA%\com.zvonochek.app\`; логи — `logs`, обновления — `update`): `settings.json`, `history.json` (журнал звонков), `vault.json` (ключ данных), ключом данных (`ZVK1`; раньше DPAPI) —
  `identity.dat` (мастер-сид), `links.dat` (ссылки), `contacts.dat` (контакты, ключи пар, ящики); `chats.db` (SQLite,
  WAL: `msgs`, `outbox`, `files`, `kv` — курсор ящика). Файлы из чатов — `Загрузки\ZVONochek`.
- Запись JSON — атомарно (временный файл + rename); испорченный файл откладывается в `.broken`, приложение стартует с чистого.
- Секреты (ссылки, парные) в БД шифруются ключом из мастер-ключа; остальное лежит открыто в профиле пользователя (обычно для десктоп-мессенджеров).
- Перенос на другой ПК — файл профиля `.zvp` под паролем (Argon2id 64 МиБ + XChaCha20-Poly1305): личность, контакты,
  ссылки, настройки, журнал и переписка; применяется при перезапуске (ADR-0003).
- Логи без секретов: ссылки и ключи не пишутся никогда, топики — только хешем.

## 14. Безопасность и приватность

| Угроза | Мера |
|---|---|
| Посторонний узнал ссылку | может позвонить, но не подслушать чужой звонок (DTLS); «Сменить ссылку»; входящие никогда не принимаются сами |
| Подмена на сигналинге (брокеры, реле, Worker) | видят только шифротекст AES-GCM, без секрета не подделать; DTLS-отпечатки сверяются кодом безопасности |
| Подмена контакта | EndpointId аутентифицируется TLS iroh / Noise libp2p; код безопасности контакта |
| Спам и DoS | P2P принимаем только от контактов, участников комнаты и по коду приглашения; лимиты частоты, размеров (256 КБ кадр, 1200 Б датаграмма), таймауты |
| Метаданные | публичные серверы видят IP, хеши топиков, время и объём; релеи n0 и DHT — ID устройства и IP. Цена бесплатной инфраструктуры — честно пишем в README |
| Доступ к ПК / флешке | секреты зашифрованы ключом данных; без пароля профиля он открывается только под той же учётной записью Windows, с паролем «Не спрашивать на этом компьютере» можно выключить; переписка (`chats.db`) пока открыта |
| Поддельное обновление | подпись exe (Ed25519) проверяется до замены, размер — по манифесту; закрытый ключ только в GitHub Secrets |
| Атаки через WebView | строгий CSP без внешних источников, весь JS локальный, IPC только своим окнам, внешние ссылки — в браузер, `zvonochek://` разбирается строго |

## 15. Сеть: порты, лимиты, ТСПУ, диагностика

| Порт (по умолчанию, меняется) | Назначение |
|---|---|
| UDP 47321 | iroh (QUIC) |
| TCP + UDP 47322 | libp2p (TCP, QUIC) |
| TCP 47329 | маяк VirtualBox (из 3.0) |
| UDP 5353 | mDNS |

Исходящие: 443 (WSS/HTTPS: Worker, Nostr, ntfy, релеи), 8084/8884/8081 (MQTT WSS), 1883 (MQTT TCP), 3478 и др. (STUN/TURN), UDP (P2P).

**Лимиты бесплатной инфраструктуры**
- Worker веба (бесплатный план Cloudflare, лимит запросов в сутки на всех): в простое — только WebSocket, HTTP-опрос — лишь в звонке или при сбое WS.
- Публичные MQTT, Nostr, ntfy — «честное использование»: бюджеты как в вебе, голос не через ntfy, редкий пульс в простое.
- Релеи n0 — бесплатно, с лимитами, без гарантий: основной путь — прямой; в настройках можно указать свой iroh-relay.
- IPFS DHT — клиентский режим, чужие записи не храним.

**ТСПУ (Россия)**
- TLS-соединения к зарубежным адресам (включая Cloudflare) «замерзают» после ~16 КБ — поэтому ротация WSS каждые 9 КБ, как в вебе,
  и дублёры MQTT по TCP 1883 без TLS.
- Зарубежные релеи n0/IPFS могут страдать так же → для пользователей из РФ важнее прямые пути; замеряем встроенным сетевым тестом с M1.
- Прямые соединения между домашними и мобильными адресами внутри РФ это, по наблюдениям, не затрагивает.

**Диагностика**
- Каналы (состояние, RTT, байты, ротации), NAT (отчёт iroh: UDP, IPv4/IPv6, тип NAT; AutoNAT libp2p), релеи и задержки, узлы DHT,
  текущий маршрут звонка, статистика WebRTC (как `callstats` веба).
- «Сетевой тест» одной кнопкой и «Экспорт диагностики» (zip без секретов) — чтобы присылать мне.
